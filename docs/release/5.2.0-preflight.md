## Reproducción sin desplegar

PowerShell, JDK 17 disponible en `JAVA_HOME`, Android SDK y firma local existente:

```powershell
./scripts/release-preflight.ps1
```

Para incluir la suite web y reglas, usando las dependencias ya instaladas del repo
web, Firebase CLI y Java 21 (argumentos explícitos; no cambia Java global):

```powershell
./scripts/release-preflight.ps1 `
  -WebRepoPath 'D:/Documents/Projects/angular/NullSiteWeb' `
  -Java21Home 'C:/Users/ricar/.jdks/ms-21.0.10'
```

Reglas: proyecto demo `demo-nullsite-phase2`, puertos aislados 18085/19195,
hub 14400/logging 14500. Si están ocupados, fallar y revisar; no detener servicios
ajenos. El JSON temporal permanece en `build/` ignorado. El script no instala
dependencias, publica, sube mapping ni muestra secretos. Las suites web y reglas
se ejecutaron por separado en esta sesión; se ejecutó completo el preflight
Android. Las pruebas UI se ejecutaron adicionalmente mediante instrumentation.

## Controles pendientes ANTES de autorizar publicación

1. Validar manualmente con admin real en entorno autorizado: inicio/cierre de
   sesión web, blog HTML/imágenes, publicar/retirar y legal publicar/rebase/historial.
   Confirmar las reglas desplegadas coinciden con el contrato web revisado.
2. Completar aceptación remota pendiente de fases 1–4 (conflictos, archivos y
   migración Room), muerte de proceso y dispositivos API 34–36. Revisar TalkBack.
3. Configurar **required reviewers** del environment GitHub `production` antes
   de cualquier push a main. Declararlo en YAML NO configura revisores.
4. **Peligro: el workflow existente en push a main despliega a Play Production
   con `status: completed`.** No usar push como simple respaldo ni asumir staging.
5. Verificar los secretos existentes de Firebase, URL HTTPS raíz, perfil, firma y
   cuenta de servicio Play. No versionar `local.properties`, JSON privado ni claves.
6. Comparar certificado de firma con la upload key Play y confirmar package
   `com.nullpointer.nullsiteadmin`. CI usa `1000 + github.run_number`: debe ser
   superior al máximo publicado. Si no, corregirlo antes de ejecutar la release.
7. Ejecutar CI limpio tras revisión/autorización; conserva AAB 14 días y falla
   si falta. Archivar AAB, hash y mapping del MISMO build, no mezclar el local con CI.
8. Revisar ficha, privacidad/Data Safety, compatibilidad y requisitos actuales de
   Play en consola. No se verificó elegibilidad de publicación ni permisos remotos.
9. Tras publicar autorizado: smoke test, métricas/Crashlytics y plan de mitigación.
   Play no admite volver a subir un versionCode menor: cualquier corrección exige
   un nuevo código superior. No migrar/eliminar datos para revertir esta UI.

## Key Learnings:

1. Un build firmado local no demuestra autorización ni elegibilidad para Play.
2. El gate `environment: production` requiere revisores configurados fuera del YAML.
3. La publicación editorial se mantiene en web para conservar sanitización,
   historial e imágenes versionadas; Android guarda únicamente el borrador privado.
